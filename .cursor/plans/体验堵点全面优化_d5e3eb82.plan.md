# 体验堵点全面优化方案

## 现状诊断

当前从「创建 Action → 分配到泳道 → 用户执行」的全链路存在以下堵点：

1. **泳道无优先级语义** — `DayLane` 仅有 `sortOrder`，没有优先级维度，所有任务混排在同一/多个泳道中
2. **自动分配逻辑粗糙** — `sync_day_runway` 把所有 Ready/Pending 任务塞进默认 focus 泳道，不按优先级分配
3. **Outcome 建议准确率低** — `auto_assign.rs` 仅用硬编码关键词做匹配，无法处理自然语言描述
4. **连接操作空间过小** — 卡片间距仅 8px（`KANBAN_CARD_GAP`），Handle 仅 6x6px 且默认隐藏
5. **悬浮窗颜色条被截断** — `border-left: 2px` 在 `.floating-shell` 的 `border-radius` + `overflow: hidden` 下被裁剪
6. **悬浮窗胶囊点击无响应** — compact 模式下 `FloatingLaneRow` 的 claimable 胶囊有 `onClick` 但缺少 `claim_task` 后的实际启动（只 claim 不 activate）
7. **外部任务只显示一个** — `getLaneState` 只返回第一个匹配的 external task
8. **时间/优先级输入阻力大** — `DetailPanel` 中预估时长用 `<input type="number">`，优先级 P1-P5 档位过细且用 select 交互

## 一、三档优先级模型（H / M / L）与泳道自动排列

### 设计原则

**优先级只有三档：H（高）、M（中）、L（低），默认 L。不同优先级在视觉上必须有明确区分。**

这一原则贯穿所有涉及优先级的场景：泳道行、Kanban 卡片、悬浮窗胶囊、详情面板。

### 数据模型改造

**Action.priority 从 `1-5 整数` 改为 `H/M/L` 三值枚举**

- Rust 后端新增 `PriorityLevel` 枚举：`High` / `Medium` / `Low`，DB 存储为 `"H"` / `"M"` / `"L"` 字符串，`NULL` 视为 `L`
- 前端 TS 类型：`type PriorityLevel = "H" | "M" | "L"`
- 迁移：`db.rs` 的 `migrate()` 中将旧 `priority` 整数值映射 —— `1,2 → H`，`3 → M`，`4,5,NULL → L`
- `Project` 新增 `priority: PriorityLevel` 字段（默认 `L`），通过 `ensure_column` 迁移
- `DayLane` 新增 `priority_tier: PriorityLevel` 字段，与泳道位置绑定

### 综合优先级评分

在 [`recommend.rs`](src-tauri/src/recommend.rs) 提取独立的 `compute_action_priority_score` 函数：

```
综合分 = action_priority_weight          // H=300, M=150, L=50
       + blocked_count * 10               // 阻塞下游任务数
       + project_priority_weight * 30     // 项目优先级 H=3, M=2, L=1
       + branch_staleness * 3             // 目标停滞度
       + pinned_bonus (1000)              // 置顶加分
       + deadline_urgency                 // 预留：截止日期紧迫度
```

### 视觉区分方案

| 档位 | 颜色语义 | 泳道行 | Kanban 卡片 | 悬浮窗 |
|------|---------|--------|------------|--------|
| **H** | 红/橙系 `--priority-high` | 左侧粗色条 3px + 背景微染 | 左侧红色粗边框 + 标签徽章 | 胶囊高亮填充 |
| **M** | 蓝/靛系 `--priority-medium` | 左侧标准色条 2px | 左侧蓝色标准边框 | 胶囊描边 |
| **L** | 灰/透明 `--priority-low` | 无色条或极浅灰 | 默认无色边框 | 胶囊素色 |

CSS 变量在 `theme.css` 中统一定义，确保深色/浅色主题一致。

### 泳道自动排列

改造 [`db.rs` 的 `sync_day_runway`](src-tauri/src/db.rs)（~L1347）：

1. 计算所有 Ready/Pending Action 的综合分
2. 按 Action 自身的 `priority` 直接决定泳道归属：H → 高档泳道，M → 中档泳道，L → 低档泳道
3. 首次打开时，若无泳道则自动创建三条 focus 泳道（命名「重要」「日常」「可选」），`priority_tier` 分别为 H/M/L
4. 保留手动拖拽覆盖 — 手动调整过位置的 Action 打 `sticky` 标记，不被自动重新分配
5. 泳道从上到下按 priority_tier H → M → L → watch 排列

### 前端改动

- 泳道标题旁显示优先级标签徽章（颜色区分，不仅是文字）
- 新建泳道时默认档位 `M`，可切换
- 拖拽 Action 跨泳道时，自动更新 Action 的 `priority` 为目标泳道的 `priority_tier`

## 二、全链路自动化堵点修复

### 2.1 Outcome 自动建议 — 引入轻量 LLM SDK

当前 [`auto_assign.rs`](src-tauri/src/auto_assign.rs) 用硬编码关键词匹配，准确率低。

**方案：接入轻量 LLM SDK，带 agentic 能力**

#### SDK 选型

使用 Rust 生态的轻量 HTTP LLM client（如 `async-openai` 或直接 `reqwest` + OpenAI-compatible API），支持：
- OpenAI / Claude / Ollama / 任意 OpenAI-compatible endpoint
- Tool calling（agentic 能力基础），为后续扩展预留（如自动拆分 Action、自动设置时长等）
- Streaming 响应（后续可用于更复杂的交互）

#### 统一 LLM 配置管理

**后端**：`app_settings` 表新增以下 key：

| Key | 说明 | 默认值 |
|-----|------|--------|
| `llm_enabled` | 是否启用 LLM | `"false"` |
| `llm_endpoint` | API base URL | `"https://api.openai.com/v1"` |
| `llm_api_key` | API Key（加密存储） | `""` |
| `llm_model` | 模型名称 | `"gpt-4o-mini"` |

新增 IPC 命令：
- `get_llm_config` / `set_llm_config` — 读写配置
- `test_llm_connection` — 验证 endpoint + key 可用性

**前端 Settings UI**：在主窗口新增「AI 设置」面板（或在侧边栏底部入口）：
- Endpoint 输入框（预填常用选项：OpenAI / Claude / Ollama local）
- API Key 密码输入框
- Model 名称输入框（带下拉建议）
- 「测试连接」按钮 + 状态指示
- 全局开关

#### Outcome 建议流程

- 新增 Rust 模块 `src-tauri/src/llm.rs`：封装统一 LLM 调用接口
- `llm_suggest_outcome` 函数：用 tool calling 让 LLM 从 Outcome 列表中选择最匹配的
- 输入：Action 标题 + 所有 Outcome 列表（id+name）+ 项目名
- 输出：建议的 Outcome ID + 置信度 + 简短理由
- 降级策略：LLM 不可用 / 超时 / 报错时 fallback 到现有关键词匹配
- 前端在创建 Action 后，如果 LLM 置信度 > 0.8，自动分配到建议的 Outcome（显示 toast 可 undo）

#### 后续 Agentic 扩展点（本期预留接口，不实现）

- 自动从 Action 标题推断时长估计
- 自动拆分模糊 Action 为具体步骤
- 根据上下文自动设置优先级

### 2.2 创建后自动进入泳道

当前流程：创建 Action → 放到 Inbox → 用户手动选 Outcome → 手动加入泳道。

**优化后：创建 Action → 自动建议 Outcome（接受/跳过）→ 自动计算优先级分数 → 自动分配到对应泳道**

- 在 `create_task` IPC 命令返回后，如果 Action 有 Outcome，自动触发一次泳道分配
- 新增 `auto_slot_action_to_lane` 函数：根据综合分找到合适的泳道，将 Action 插入

### 2.3 完成后推荐的智能化

当前 `compute_recommendations` 已有评分，但推荐列表展示在悬浮窗不够直观。

- 完成一个 Action 后，自动将同泳道的下一个 Ready Action 标记为 claimable 并高亮推荐
- 如果泳道空了，从其他泳道的下一推荐中提示

## 三、UI 体验细节修复

### 3.1 项目竖列 UI 优化

当前 KanbanBoard 用 ReactFlow 渲染列，列宽 196px，卡片 180x76px。问题：列头样式粗糙，缺少分隔感。

改动点：
- [`KanbanBoard.css`](src/components/project/KanbanBoard.css) 的 `.kanban-board__column-bg` 增加背景渐变和圆角
- [`OutcomeColumnHeader`](src/components/dag/LaneLabelNode.tsx) 优化排版：增大字号，添加进度条，增加更好的间距
- 列间增加细分割线，替代当前的纯透明间距

### 3.2 Action 连接操作体验

当前问题：`KANBAN_CARD_GAP = 8px`，Handle 仅 6x6px 且隐藏，用户很难从卡片底部连到下一个卡片顶部。

**方案：连接入口从「点对点拖拽」改为「卡片上下文菜单」**

- 增大 Handle 可交互区域：visible area 保持 6px 但 hit area 扩大到 16x16px（通过透明 padding）
- 将 `KANBAN_CARD_GAP` 从 8px 增大到 16px，给连线操作留出空间
- 同时在 ActionNode hover 时显示「添加依赖」按钮，点击后进入选择模式（从列表中选择目标 Action）

### 3.3 悬浮窗颜色条修复

当前 `.floating__lane-row` 使用 `border-left: 2px`，被外层 `.floating-shell` 的 `border-radius` 和 `overflow: hidden` 截断。

**方案：将 `border-left` 改为内部伪元素**

```css
.floating__lane-row {
  border-left: none;
  position: relative;
  padding-left: 10px;  /* 原来是 8px */
}
.floating__lane-row::before {
  content: '';
  position: absolute;
  left: 4px;       /* 不贴窗体边缘 */
  top: 4px;
  bottom: 4px;
  width: 2px;
  border-radius: 1px;
  background: var(--lane-accent, var(--lane-focus-accent));
}
```

### 3.4 悬浮窗胶囊点击启动

在 [`FloatingLaneRow.tsx`](src/components/floating/FloatingLaneRow.tsx)（~L77），`onClaim` 只执行 `claim_task`（将 Action 设为 active），但 UI 上没有后续反馈。

修复：
- `onClaim` 调用后，前端刷新 snapshot + 显示 toast "已开始: {action.title}"
- 在 `FloatingWidget.tsx` 的 `claim` 函数（L155-158）中增加 `showFeedback` 调用

## 四、悬浮窗外部任务多个显示

### 现状问题

[`getLaneState`](src/components/runway/runwayTaskUtils.ts)（L192-210）对 external 状态只返回第一个匹配的 task。悬浮窗因此只展示一个等待外部的任务。

### 方案

- 新增 `getLaneExternalTasks` 函数，返回所有 external 状态的 tasks 数组
- 修改 `FloatingLaneRow`：当 `state === "external"` 时，渲染所有 external tasks 而非仅一个
- 外部任务列表展示为可折叠的简洁列表，每项带「标记完成」按钮
- Watch 泳道特殊处理：watch 泳道本身就是用来显示多个外部任务的，改为列表形式展示

## 五、快速选择替代手动输入

### 5.1 预估时长

将 [`DetailPanel.tsx`](src/components/detail/DetailPanel.tsx) L127-136 的 `<input type="number">` 替换为预设选项组：

```
[5min] [15min] [30min] [1h] [2h] [自定义...]
```

- 用 `button` 组实现，点击即设置，不需要额外确认
- 「自定义」展开数字输入框

### 5.2 优先级设置

将 L138-154 的 `<select>` 替换为三档横排按钮组：

```
[H 重要] [M 普通] [L 可选]
```

- 三个按钮用对应优先级颜色填充/描边，视觉即区分
- 当前选中态：填充色 + 加粗；未选中态：ghost 描边
- `onCyclePriority` 改为三档循环：L → M → H → L
- `taskUtils.ts` 的 `nextPriority` 更新为 `"L" → "M" → "H" → "L"`

### 5.3 创建 Action 时的快速属性设置

当前 `AddTaskInline` 和悬浮窗创建只输入标题。增加创建后的内联属性设置：
- 创建后在原位展示一行快速设置：时长预设 + 优先级三档按钮
- 3 秒内无操作自动折叠（使用默认值 30min / L）
